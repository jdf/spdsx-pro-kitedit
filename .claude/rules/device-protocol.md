# SPD-SX PRO device protocol reference

Byte-level protocol facts moved out of the root CLAUDE.md (2026-07-27, /doctor).
Everything here is capture-derived and live-verified as dated; treat it as ground
truth over guesses. The root CLAUDE.md keeps the sync-engine status, firmware
gate, and per-file architecture notes.

## Kit record storage & write maps

- **Kit record layout** (RE'd 2026-07-12, ground-truth verified: ZZZ kit = #129 and edited pad values read back exactly): bank 0x10, clean (header-stripped) image, array base **0x262c**, stride **3528** bytes, **200** records; name = first **16** bytes (space-padded ASCII). Per-pad param table at **rec+0x284**, 9 pads × **28-byte** blocks; within a block the byte offset = the DT1 param index: +0x00 layer mode (MIX=0…HI-HAT=7), +0x01 fade point, +0x02 fade end, +0x03 dynamics on/off, +0x04 dynamics curve (LINEAR=0…LOUD3=3), +0x05 **fixed velocity** (used when dynamics off), +0x07/+0x08/+0x09 hi-hat closed-pedal **volume/fade-in/decay** (mapped live 2026-07-13 by capturing the app's writes on a hi-hat pad — this supersedes and corrects the earlier +0x06/07/08 fade-in/volume/decay guess, which was off by one and mislabeled; USER KIT stores volume 80 @0x07, fade-in 0 @0x08, decay 25 @0x09), **+0x0c/+0x0d the DIRECTIONAL pad-link pair: send group @0x0c, receive group @0x0d, 0 = none, SAME offsets for pads and triggers** (mapped live 2026-07-27 on kit 199 ground truth: pad 3 'send group 3' landed at +0x0c, trigger 1 'receive group 3' at +0x0d; the earlier one-field model was wrong — link_all_kits.py's pad writes at 0x0d were the RECEIVE half and its trigger writes at 0x0c the SEND half, which is why trigger-hits fired pads), +0x13 trigger reserve. **TRIGGERS ARE STRUCTURALLY PADS** (probed offline 2026-07-27): their 8 × 28-byte table at **rec+0x380** mirrors the pad blocks field for field — same offsets for mode/fades/dynamics/curve/fixed-velocity/hi-hat trio — except the link group sits at **+0x0c** (= its DT1 param index; pads use 0x0d), and their layers CONTINUE the layer table as **blocks 18–33** (trigger t top = block 18+2t; kit 1's trigger 1 carries wave 201 in the cached image, and preload kits show consecutive pool waves across trigger layer blocks). Modeled as full `Pad`s: `KitRecord::triggers`, KitModel objects 9–16, document schema v5 pads rows 9–16. Write addressing generalized by `ObjectKind`: param page `0x28+t` (link write live-verified), layer slot bytes presumed `0x52+2·(t−1)+layer` continuing the pad sequence — **trigger param/wave writes NOT yet live-verified**. `device/kit_image` parses names + these into `KitRecord`; `SpdsxDevice::SetPadLayerParams` writes them. **Per-layer table at rec+0x49a** (mapped 2026-07-12 offline against the ZZZ-kit ground truth): 18 layers (9 pads × top/bottom) × 60-byte blocks, each starting with the layer's WAVE (pool index, u16 LE, 0 = none). EQ/effects/kit-level settings still unmapped (same diff method). `spdutil kits [--from <dump>]` lists names; `spdutil kit <N> [--from <dump>]` shows a kit's pad params.
- **Pad-param WRITE map** (captured live via `re/frida-scripts/paramlog.js`, 2026-07-12): DT1 `<kit-prefix> <0x1F+pad> <param>` with the SAME param index as storage. **The first two address bytes are the kit** (`PadLinkPrefix(kit)` = `512+2*(kit-1)` split 7-bit) — captures were on kit 129 so they show `06 00`, which is exactly kit 129's prefix; the writes are kit-absolute, NOT current-kit-relative (corrected 2026-07-13 after every write initially hit kit 129). Values match the enums 1:1. Ported: `SetPadLayerParams`/`SetPadWave`/`SetKitName` build the kit prefix, no SelectKit needed.
- **Flash-commit handshake — the WRITE button DOES send serial commands** (corrected 2026-07-12; an earlier note wrongly said "nothing sent" because an `isPoll` filter suppressed all `6a 03` frames, eating exactly these). On WRITE the app sends, on ch 0x09 control family: `f0 41 6a 03 21 ...` (begin commit) → device acks `f0 41 6a 7a ...`; then it polls `f0 41 6a 03 22 ...` every ~250ms, each answered `f0 41 6a 02 ... 22 40 00 00 00 04 <status LE32> f7` with status 0 while busy, flipping to 1 when the flash write completes (~1.8s). So durable sync WRITE = the mapped DT1 param writes, THEN `6a 03 21` + poll `6a 03 22` until status==1. (Bonus from the same capture: `6a 03 cat=17` returns the firmware version ASCII, e.g. "2.00"/"0094" — cracks `spdutil info`. `7a` replies are generic ACKs, seen on both 6a and 6c families.) Full capture: `../re-cache/captures/writecmd-commit-handshake.log`.

## Reverse-engineering method & tooling

NOT MIDI — it's Roland DT1 SysEx wrapped in a proprietary transport frame over USB CDC-ACM serial (230400 baud). See `[[project-spdsx-patchedit]]` memory for the full protocol map. Cracked so far: kit select, object focus, pad-link, kit name (read+write), pad wave assignment (read+write, nibble-encoded), per-pad layer params (read+write — the kit-record layout above), the full bulk-read handshake, the flash-commit (WRITE) handshake, and the firmware-version query. Device state = ~8MB bulk block transfer on the `41 6c` family, banked; the cached image holds TWO passes of every bank (the app's load runs twice), so per-pass sizes are half the totals. 0x10 = kit/settings (~0.7MB/pass, 3528-byte-per-kit records); 0x20 = the **sample-pool DIRECTORY, not audio** (~3.3MB/pass: 20001 × 164-byte records — wavename/filename/frames/category + an opaque u64 pointer into device flash — then category + user-tag name tables; layout in `device/sample_image.h`). **No wave audio crosses in the state dump at all**, and the official app bundle ships none either: sample download/upload is a separate, still-uncaptured protocol. Method to map a parameter: dump image, change ONE thing in the official app, dump again, diff. Capture + RE tooling lives in **`re/`** (frida capture scripts, `parse_capture.py`, and the original `spdsx.py`/`link_all_kits.py` Python reference this C++ was ported from; see `re/README.md`). frida at `~/frida-env/bin/frida`, SIP disabled; keep attached via `tail -f /dev/null | frida -f <app> -l <script>`. An offline ~8MB device image is cached at **`../re-cache/device-image.bin`** with a memo — the source for all documented storage offsets. jdf drives the GUI + hardware for captures. (Also mirrored at github.com/jdf/spdsx-py.)

**Live transport VERIFIED** (2026-07-11, re-verified after the spdutil rename): `spdutil ping` opened the port and pinged the real device, which replied byte-identically to the frida capture (`f0 41 6a 02 ... 16 40 00 00 00 04 01 00 00 00 f7`). So the whole C++ transport stack (serial open + baud ioctl, frame wrap/unwrap, round-trip) works against hardware. The `/dev/cu.usbmodem<N>` node number changes every replug — there is no stable path; with no `--port`, spdutil scans `/dev/cu.usbmodem*` and pings each node until the device answers. Close the official app first (one program per port). Bulk reads are exercised live too (`spdutil dump` / `kits` / `kit <N>` all ran against hardware 2026-07-12); the write paths (SetKitName/SetPadWave) are still unexercised live.


## Protocol details (moved from Open items)

- **Sample AUDIO transfer — read/download/delete AND upload all DONE + live-verified** (2026-07-13). Full protocol in `../re-cache/captures/WAVE-EXPORT-PROTOCOL.md` + `WAVE-UPLOAD-DELETE-PROTOCOL.md`. Read/download (any index, preloads included), local cache, playback, delete: shipped. **Upload is one atomic action** — `SpdsxDevice::UploadWave` (file write via `WriteRemoteFile` + directory registration via `RegisterWave`, both private) driven by `spdutil sendwave <N> --from f.smp [--name X.wav]`. Register = finalize temp, `6a 03 0b`/`0c arg=N`, two DT1 directory records into the block at **0x2000000 + N·256** (4×7-bit addr; base record @+0x00 carries the sample END POINT as five big-endian nibbles at 0x0b..0x0f = the per-channel frame count (NOT frames/4096 — that was wrong and truncated playback; decoded 2026-07-21), name record @+0x1b carries wavename[16]+filename[100]+the 32-bit hash field), then flash `Commit`. `protocol.cc` has `SampleRecordAddr`/`SampleBaseRecord`/`SampleNameRecord`, byte-exact vs the capture and guarded by `device/protocol_test.cc`. **The record's 32-bit "content hash" turned out to be a red herring: the device stores it verbatim and ignores it — a sample uploaded with that field = 0 registers, is measured, and PLAYS on the unit** (live-verified; jdf confirmed 1590). So we always write 0; no hash to crack. The frame-count in a bank-0x20 dump lags one commit (image coherency), not a field we write. To build a playable `.SMP` from arbitrary PCM, `device::PcmToRfwv` writes the RFWV header + an **MD5 checksum at header 0x20..0x2f = MD5(header[0x04..0x13])** which the device validates before playing (wrong/zero = silent); the 0x30..0x1ff overview block is not needed. The device plays **48 kHz / 16-bit only** (it stores other rates/depths verbatim but won't play them; channels are kept — stereo plays), so the upload path resamples local files to 48k/16-bit first via `source/sample_upload.cc` (`SmpFromAudioFile`). **WRITE-DATA FRAME CAP = 64 KiB** (`import-large-1.log`): a `03/06` write-data frame carries at most 65536 bytes; larger PCM streams as a back-to-back burst of 64 KiB frames with ONE ack. **The one ack hinges on the body's marker byte (found live 2026-07-22): continuation frames of a burst carry `00 00` before the length septets; ONLY the final frame of a write carries `40 00` = "end of write, ack now". Stamping `40` on every chunk makes the device ack every chunk, which desyncs everything after the burst (this masqueraded as "verify fails after a multi-frame file").** **BATCH UPLOAD — the full faithful sequence (mapped 2026-07-21 from `import-multi-1.log`, 16 samples in one session, live-verified 12-on-one-connection all byte-exact).** The earlier minimal subset wedged the device after ~3 uploads (later samples registered metadata but no audio); the lesson (jdf's) is REPLICATE THE OFFICIAL APP EXACTLY, skip nothing. **Refined 2026-07-22 by a full protocol-fidelity audit of every capture** (findings + fixes below marked AUDIT). Per file, `UploadWave` opens the session — **`6a 09(arg=1)` + `6a 0a`** (AUDIT: this pair is the per-file session OPEN; the old code sent it as a trailing "finalize" and never sent the close). Then `WriteRemoteFile`: stat `.TMP` (0a), **create (0x18) with TWO 200-byte path fields — `.SMP` then `.TMP`** (a single 400-byte field left .TMP zero and the file never persisted), then **dir D0NN (0c)**: an existing directory answers a handle at reply bytes 4..8 → echo it (0d) and open; a MISSING one answers all-zero and only then does the **mkdir walk** run — dir DATA (0c → the PARENT's handle), 0d(parent handle), dir D0NN, mkdir D0NN (0x09 file-channel), dir D0NN (0c→handle), 0d(handle) (AUDIT: the walk is conditional, and in the walk the first 0d echoes the parent's handle, not the missing dir's zeros). Then open-write (0x00), seek 512, **free-space query (0x19, PathBody `/SPDSXREMOTE//`) whose reply is TWO things: a raw 16-byte 0c-prefixed off-format fragment (ReadExact(16)) AND a normal ack frame (ReadFrame)** — AUDIT: not consuming the ack frame ran the whole rest of the upload one ack behind (the old "base record rides on a delayed frame" mystery). Then write PCM (chunked), seek 0, write header, close. Then `RegisterWave`: finalize `.TMP` (0a), `6a 0b`/`0c arg=N`, base DT1 record @+0x00 (Send, no ack), **`6a 09(arg=0)` session CLOSE** (its ack is the barrier), name DT1 record @+0x1b (Send, no ack) — AUDIT: the `6a 15/16` pair the old code sent between the records was the official app's background status poll cargo-culted into the sequence while the real 09(arg=0) was missed. The device commits ONE flash write for the WHOLE batch: `PrepareUploadBatch()` (one `6a 0d` last-index query — the official batch preamble) up front, every `UploadWave` into working state, then a single **`CommitUploadBatch()` = `6a 21`, `6a 0c(arg=1)`, `6a 02`, then `6a 22` poll** (AUDIT: the import commit carries those two extra messages in every capture; a plain WRITE/delete `Commit()` is just 21+22-poll) — `ExecutePush` and `spdutil sendwave` (multi-`--from`) both do this. Committing per file is what wedged the unit. Records: base @+0x00 carries the sample END POINT as five big-endian nibbles at 0x0b..0x0f = per-channel frame count (the old 0x0c=frames/4096 truncated playback; fixed 2026-07-21); name @+0x1b = wavename[16]+filename[100]+a 32-bit hash we write as 0 (device ignores it); the base record's own name/filename fields are just the official app round-tripping stale cached records — our space/zero template equals a previously-empty slot. **DT1s are NEVER acked, period** (no capture has a device frame on the DT1 channel except unsolicited notifications): records, param writes, kit-select and object-select all go out fire-and-forget — `SelectKit`/`SelectObject` waiting 0.4s each was pure stall (AUDIT). `PcmToRfwv` builds the `.SMP`: RFWV header + MD5 at 0x20..0x2f = MD5(header[0x04..0x13]) which the device validates (wrong/zero = silent). Device plays **48k/16-bit only**; `SmpFromAudioFile` resamples with a **windowed-sinc** interpolator (Lagrange rolled off the treble). (Note: `WAVE-EXPORT-PROTOCOL.md`/`WAVE-UPLOAD-DELETE-PROTOCOL.md` don't exist in re-cache/captures — only `BULK-READ-PROTOCOL.md` + the raw `.log`s; upload is reconstructable from `synthupload-1.log`, `import-large-1.log`, `import-multi-1.log`.)
- **CURRENT KIT (read) — found 2026-07-22**: the device's active kit is the FIRST u16 LE of the kits bank's clean image, 0-based (kit 5 → `04 00`; the single byte that changes across a kit switch — diffed dumps prove it). No RQ1 support exists (probed live: silence), and the `6a 17`/`6a 26` ASCII query families are static info (17: 0="2.00" 1="1020" 2="2.00" 3="0094", rest "----"; 26: 4="0002" 6="0003" 7="0009", rest "0000"). `SpdsxDevice::CurrentKit()` streams only the bank's first READ batch (sub-second); `spdutil currentkit` prints it; the app adopts the unit's kit on every disconnected→connected transition (no echo back). Bank 0x30 (7.8 KB) mirrors the ACTIVE kit's contents + global state (tempo u16 LE ×10 at clean +0x0a-ish; kit name at ~+0x318) but NOT the kit number; bank 0x40 is 65 bytes of config.
- **PER-LAYER PARAMETER PAGE — fully mapped 2026-07-22** (`layerparams-1.log`: jdf swept each official-app layer-editor control in order). DT1 page `<kit prefix> <0x40+2·(pad−1)+layer> <offset>`: 0x00 Layer Sw (the enable flag), 0x01 wave (4 nibbles), **0x05 Volume (s16 nibbles, 0.1 dB units)**, 0x09 Pan (s8, 0=center), 0x0b/0x0d Pitch Coarse/Fine, 0x10 DelaySync, 0x12 DelayTime (u16 nibbles, ms), 0x16 Poly/Mono, **0x17 Fade In (0-127)**, **0x18 Decay (0-127, 127=none)**, 0x19 Loop, 0x1a Trigger Type, 0x41 Mode. Constants in protocol.h (`kLayer*Offset`); `PadLayerAddr` builds addresses; `SpdsxDevice::SetPadLayerMix` writes the volume/fade-in/decay trio; `spdutil setlayer --kits K --pad P.S [--volume dB] [--fadein N] [--decay N] [--commit]` drives it (live-verified round-trip; whatever you leave out is read off the device and written back unchanged). **Kit-RECORD offsets differ from the DT1 page**: within the 60-byte layer block (base 0x49a, stride 60): wave u16 LE @+0x00, **volume s16 LE @+0x02, fade-in @+0x0d, decay @+0x0e** (located by writing distinctive values and finding them in a fresh dump); ParseKits fills `PadDeviceParams::LayerMix` per layer. NOTE the general lesson: DT1 write addresses and record storage offsets are SEPARATE layouts for the layer table (unlike the pad-param table where param index == record offset).
- **Wave EXPORT and DELETE — official-faithful as of the 2026-07-22 audit.** `ReadRemoteWave` follows `waveexport-1/2.log` exactly: **session open `6a 09(1)` + `6a 0a`**, OPEN, seek 0, **read the 512-byte RFWV header FIRST (read length = 3 big-endian septets at body bytes 7..9: 512 = `00 04 00`)**, THEN stat (13) for the size, seek 512, read the remainder in **exact-size** requests of ≤512 KiB (`20 00 00`), CLOSE, **session close `6a 09(0)`** — the old code skipped the bracket entirely, statted first, and over-asked. Seek offsets use the same septet body. `DeleteWave` follows `fileops-1.log`: `6a 0c(arg=N)` slot query, `6a 0d` last-index query, session open `09(1)`, `6a 1d(arg=N)` delete, then **drain until quiet — deleting an assigned wave makes the device push unsolicited DT1 notifications** (kit-select echo + assignment clears) that would otherwise be misread as later acks, then `6a 18` + `6a 23` status queries, session close `09(0)`, plain `Commit()`.
- EQ, effects, and the kit-level settings block are still unmapped — same method: dump, change ONE thing in the official app, dump, diff (`../re-cache/captures/BULK-READ-PROTOCOL.md` + logs hold the decoded handshake evidence).
